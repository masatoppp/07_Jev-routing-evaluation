# 07｜Jevによるルーティングの検証

Jev（TypeSafe AI）の `Choice` を使い、ユーザーの質問を **LLM／Web検索／RAG／判定不能** の4種類に分類するルーティングエージェントを実装しました。

本作品の中心は、**JevとGPT-4.1-mini（Structured Outputs）のルーティング判定を比較評価すること**です。人手で正解ラベルを付けた30件の質問を用い、判定精度・処理時間・トークン使用量・APIコストを検証しました。回答生成やRAG検索そのものの性能比較は対象外です。

## システム構成

```text
                         ユーザーの質問
                               │
                               ▼
                     Jev（Choice）で分類
                               │
          ┌────────────┬────────┴───────┬────────────┐
          ▼            ▼                ▼            ▼
        llm           web              rag         unknown
          │            │                │            │
    GPT-4.1-mini   Tavily検索       ChromaDB検索    質問の確認
      で回答         │                │          を求める
                   検索結果を        文書を根拠に
                 GPT-4.1-miniへ    GPT-4.1-miniで
                     渡し回答          回答
```

| 分類 | 判定基準 |
|---|---|
| `llm` | 一般知識で回答できる質問 |
| `web` | 最新情報やリアルタイム情報のWeb検索が必要な質問 |
| `rag` | 社内文書や社内規定の参照が必要な質問 |
| `unknown` | 意味不明な文字列や、文脈不足で意図を判断できない入力 |

ルーティング結果に応じて処理を呼び分ける構成とし、LangChain／LangGraphは使用していません。

## 使用技術

| 用途 | 技術 |
|---|---|
| ルーティング判定 | Jev（TypeSafe AI、`Choice`） |
| 比較対象モデル | OpenAI `gpt-4.1-mini`（Structured Outputs） |
| 回答生成 | OpenAI `gpt-4.1-mini` |
| Web検索 | Tavily |
| RAGのEmbedding | `intfloat/multilingual-e5-base`（Sentence Transformers） |
| ベクトルデータベース | ChromaDB |
| 分析・可視化 | pandas、matplotlib |
| 開発環境 | Python 3.11、Jupyter Notebook |

## RAGで使用するDocument

RAGの検索対象は、**架空の社内規定・社内手続きを想定した日本語テキスト文書**です。Notebookの初期設定では、`RAG_test_data/` 以下の `.txt` ファイルをサブフォルダも含めて読み込みます。

- `Path.rglob("*.txt")` で文書を収集し、UTF-8（BOM付きも可）で読み込みます。空文書は登録しません。
- 文書は **1ファイル＝1文書** として扱い、チャンク分割は行いません。
- ファイル名（`filename`）と、`RAG_test_data/` からの相対パス（`path`）をメタデータとして保存します。
- 各文書に `passage: ` を付け、`multilingual-e5-base` でEmbeddingしてChromaDBへ `upsert()` します。
- 質問に `query: ` を付けてEmbeddingし、`collection.query()` で **上位3文書**を検索します。
- 検索した本文・ファイル名・相対パスをGPT-4.1-miniに渡して回答を生成し、参照ファイル名の提示を指示します。

ChromaDBは **RAGに振り分けられた後の検索処理**に使用し、Jev自体の判定処理には使用しません。`jev_chroma/` は実行時に生成されるDB保存フォルダであり、GitHubへの登録は不要です。公開するのは元のテキスト文書です。

**注意：** 今回のRAGはルーティング動作確認用の簡易実装です。長文のEmbedding入力上限、類似度閾値の未設定、再登録時に残る古い文書IDなどへの対応は限定的です。また、RAG回答のために取得文書がOpenAI APIへ送信されるため、実際の機密情報・個人情報を含む文書は使用しないでください。

## 比較評価

### 評価方法

人手で期待する分類を設定した **30件**を、JevとGPT-4.1-miniに入力しました。

| `llm` | `web` | `rag` | `unknown` | 合計 |
|---:|---:|---:|---:|---:|
| 8件 | 8件 | 8件 | 6件 | 30件 |

予備評価の後、両モデルに渡す分類基準の**説明文を共通化**し、改めて最終評価を行いました。ただし、Jevの`Choice`とOpenAIのStructured OutputsではAPI形式が異なります。処理時間はAPI呼び出し全体の経過時間で、純粋な推論時間ではありません。

### 最終評価結果（30件）

| 指標 | Jev | GPT-4.1-mini |
|---|---:|---:|
| 正解率 | **30/30（100%）** | **30/30（100%）** |
| 平均処理時間 | **0.397秒** | 0.983秒 |
| 平均入力トークン | 477.07 | 171.67 |
| 平均出力トークン | 46.27 | 6.27 |
| 平均合計トークン | 523.33 | 177.93 |
| 30件のルーティングAPIコスト（概算） | **$0.00060110** | $0.00236080 |

今回の条件では**両モデルとも全問正解**でした。一方、Jevの平均処理時間はGPT-4.1-miniと比べて約**2.48倍高速**で、APIコストは約**74.5%低い**という結果です。Jevの平均トークン使用量はGPT-4.1-miniより多いものの、仮定した料金ではコストが低くなりました。

コスト計算に用いた単価（USD／100万トークン）は **Jev入力 $0.042・出力 $0、GPT-4.1-mini入力 $0.40・出力 $1.60** です。いずれも検証時に採用した計算上の単価であり、現行の実請求額を保証するものではありません。**下流の回答生成、Tavily検索、Embeddingなどの費用は含みません。**

### 予備評価と判定の再現性

共通基準導入前の予備評価では、Jevは30件中30件、GPT-4.1-miniは30件中29件が正解でした。同じ質問を追加で5回ずつ判定した補助検証では、Jevは `web` が5回、GPT-4.1-miniは `web` が4回、`unknown` が1回でした。

試行数が少ないため、判定の安定性に一般的な優劣があるとは結論づけていません。

## 実行方法

### 1. ライブラリの準備

Python 3.11の環境に必要なパッケージをインストールします。

```bash
pip install jupyter typesafe-sdk openai tavily-python chromadb sentence-transformers pydantic pandas matplotlib
```

### 2. Notebookとデータの配置

`07_Jevによるルーティングの検証.ipynb` を開きます。Notebookの**現在の作業ディレクトリ**から `jev_final_evaluation.csv` と `RAG_test_data/` を参照するため、通常はリポジトリのルートでJupyterを起動します。

初期状態では以下のフラグはすべて `False` です。

| 設定 | `True` にした場合の動作 |
|---|---|
| `RUN_RAG_SETUP` | テスト文書の読み込み・Embedding・ChromaDBへの登録 |
| `RUN_API_TESTS` | Jev等のAPIを用いた動作確認 |
| `RUN_NEW_EVALUATION` | JevとOpenAIを各30回呼び出し、CSVを上書きして再評価 |
| `RUN_STABILITY_TESTS` | 同一質問の繰り返し判定 |

**最終評価を確認するだけなら、すべて `False` のままNotebookを実行できます。** この場合、保存済みのCSVを読み込んで再集計し、外部APIを呼び出しません。Notebookには共通基準導入前の予備評価データも保存されており、CSVが読み込めなければ予備評価を使用したことを明示します。

### 3. APIやRAGを実際に動かす場合

外部APIを利用する場合は、環境変数 `TYPESAFE_API_KEY`、`OPENAI_API_KEY`、`TAVILY_API_KEY` を設定してください。**認証情報はNotebookやGitHubへ記載しないでください。**

- RAGを使う場合、先に `RUN_RAG_SETUP=True` で `prepare_rag()` を実行し、テスト文書をChromaDBへ登録します。初回はEmbeddingモデルの取得が必要になる場合があります。
- `run_agent("質問文")` を実行すると、Jevが選んだルートに応じた回答処理が呼ばれます。`rag` ルートではRAGの事前準備が必要です。
- APIを用いた判定・回答生成やWeb検索は、利用状況に応じて費用が発生する可能性があります。

`RAG_test_data/` とChromaDB保存先は、それぞれ環境変数 `JEV_RAG_DATA_DIR` と `JEV_CHROMA_DIR` で変更できます。

## 評価上の制約

- 正解ラベルは人手で設定した30件のみで、曖昧な入力を広く網羅した検証ではありません。
- API応答時間には通信経路やサービス側の負荷が含まれ、モデル単体の推論速度ではありません。
- 同じ分類基準の文章を使用していますが、JevとOpenAIのAPI仕様・入力表現は完全には一致しません。
- 今回は**ルーティング結果の比較**であり、RAGの検索品質・回答品質やWeb検索の品質は測定していません。
- コスト比較は当時採用した単価に基づく概算であり、実際の運用コストとは異なる可能性があります。
